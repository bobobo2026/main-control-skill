# DSH 主控与执行会话派发

本 skill 是 `~/.codex/skills/codex-session-orchestration` 的 DSH 适配版，跨项目主控路由的**唯一事实源**。

其他 skill 可以补充业务事实、发布规则或安全边界，但**不得重述或重定义**这里的会话选择、复用、创建、命名、模型策略和派发后行为。

## 何时用哪一版

| 场景 | 用哪个 |
| --- | --- |
| 当前在 DeepSeek Harness 里，任务涉及主控/派发/路由 | **本 skill** |
| 用户明确要求按 Codex 原生流程执行，或要在 Codex 应用里派发 thread | `codex-session-orchestration`（它依赖 DSH 不存在的工具，在 DSH 里只能当参考） |

## 与 Codex 版的工具映射

适配不是翻译，是重新落地。传输层有 4 处**真实能力降级**，必须知道：

| Codex | DSH | 差异与后果 |
| --- | --- | --- |
| `$CODEX_THREAD_ID` + `~/.codex/project-main-controls.json` | `$DSH_SESSION_ID` + `~/.dsh/project-main-controls.json` | 脚本见下节；不共用注册表，命名空间不同 |
| `list_threads`（搜索项目内任意会话） | `list_agents`（本 agent 的直接子代理）+ `session_list` / `session_status`（顶层会话的元数据） | ⚠️ 必须区分**寻址**与**内容**：新工具只给 id / 标题 / cwd / 工作区 / 运行状态，**没有** `read_thread` 等价物，读不到别人会话的内容。见「双通道路由」 |
| `create_thread`（可带 `environment.type`、`title`） | `subagent(description, prompt, run_in_background)` | ⚠️ **无 worktree/隔离参数**，隔离必须写进 prompt 由子代理自己做 |
| `send_message_to_thread` | `send_message(agent_id, message)` | DSH 更强：失败即未投递 |
| `read_thread` 送达核验 | **不需要**，见「派发事务」 | Codex 需要是因为投递可能退化成 `functionCallOutput`；DSH 不会 |
| `wait_threads` / 轮询 | 明令禁止 | DSH 全局规则同样禁止 busy-poll |
| 显式传 `model` / `thinking` 参数 | 子代理**完全继承主控会话模型** | 既定策略就是"统一继承"，不需要也不允许单独指定，见「模型与权限」 |
| `clientThreadId` / setup 排队 / `::created-thread{}` | 无对应 | 全部删除，不得虚构 |
| `codex-thread-relay` 接力换新会话 | 无安全等价物 | ⚠️ 接力会**丢失全部执行子代理的寻址能力**，见「会话寿命」 |

## 会话寿命（DSH 特有约束）

Codex 版允许主控接力换新鲜上下文，因为执行 thread 在侧边栏里独立存活、任何会话都能搜到。**DSH 不行**：

- `list_agents` 只返回当前 agent 的直接子代理；`send_message` 只能投给 depth-1 子代理，更深的只能 `interrupt_agent`。
- 因此换主控会话 = 失去全部执行容器的寻址能力，既有业务域历史无法续派。
- **主控会话应长期存活**，优先在同一个主控会话内累积业务域子代理；不要把「接力换上下文」当作常规手段。
- 子代理默认嵌套上限 `maxDepth: 3`（主控 → 执行 → 更深）。主控只直接管理第 1 层。

## 自动角色检测

每个项目任务开始时运行：

```bash
ruby ~/.dsh/skills/dsh-main-control/scripts/main_control_role.rb "$PWD"
```

脚本读 `~/.dsh/project-main-controls.json`，按**最长路径前缀**匹配项目根，比较其 `main_session_id` 与 `$DSH_SESSION_ID`，返回：

- `role=main_control`：加载并遵守本 skill 全套流程后再动手。
- `role=execution`：不得自任主控，只执行被派发的范围并在自己的会话里汇报。
- `role=unconfigured`：按项目常规行为处理，不要因为「这是第一个可见任务」就假设自己是主控。
- `auto_create_execution_threads=true` 是项目级持久授权，**仅当确实没有合适执行子代理时**才允许新建；字段缺失或非字面量 `true` 一律按 `false`，逐次询问。
- 脚本已强制 UTF-8，`LANG` 未设置也不会崩（Codex 原版在这里会抛 `Encoding::InvalidByteSequenceError`）。

**绑定当前会话为主控**（用户明确指定时）：

```bash
ruby ~/.dsh/skills/dsh-main-control/scripts/register_main_control.rb "$PWD" --name "<项目名>"
```

- 只接受**真实存在**的项目根；路径写错会被拒绝，避免假装绑定成功。
- 绑定子路径时会报告被遮蔽的父条目，最长前缀仍然生效。
- `--unbind` 解绑，`--list` 查看全部绑定（标出哪个是当前会话）。
- 改动会原子写入并保留一份 `.bak`。

**命名**：DSH 没有工具让主控设置会话标题，因此 Codex 那条「主控标题必须以 `🎛️ ` 开头」**无法由 skill 保证**——需要用户在 GUI 里自行命名。不要声称已设置标题。子代理用 `description`（3-5 词，仅展示用）承载业务域短名，项目与任务编号写进 prompt 正文。

## 主控边界

当角色为 `main_control` 时：

- 所有项目细节任务一律派发到执行子代理。主控只负责：读取系统强制要求主代理亲自读取的规则、运行角色检测、识别业务域、选择或创建执行子代理、定义本次最小 MVP、一次性写好 prompt、告知用户派发结果。
- **诊断、需求分析、代码与配置检查、日志与数据库查询、浏览器操作、文档或 Base 读写、实现、测试、构建、验收取证、发布和外部回写都属于执行细节，主控不得亲自完成。**
- 除强制规则读取、角色检测，以及「已获新建授权、即将派发」时运行一次 `worktree_preflight.rb` 外，主控不得使用 `bash`、`read`、`write`、`edit`、`grep`、`glob`、`web_fetch` 等工具做项目工作。该 preflight 只能对项目根执行固定只读 Git 命令，不得读取业务文件或扩展为项目诊断。
- 主控**允许**使用：`subagent` / `send_message` / `list_agents` / `interrupt_agent`，以及必要的一次 `ask_user_question`。
- 主控**另允许**使用 dsh-bridge 的五个跨会话工具（host 平面注册，所有会话可见）：`session_list` / `session_status`（只读发现）、`session_spawn`（创建顶层可续派容器）、`session_send`（向其投递）、`session_messages`（只读**投递给本会话**的消息）。用法与边界见「双通道路由」。
- `role=main_control` 表示负责路由，**不自动代表用户授权新建**。只有确实没有合适执行子代理，且用户当前明确要求新建、或项目 `auto_create_execution_threads=true` 时，才调用 `subagent`；两项都不满足时，说明缺少承接容器并询问用户。
- 同一业务域子代理正在执行其它 MVP 时，仍然优先向其续派或排队；**「正在运行」不是创建编号副本的理由**。
- 主控没有「任务很小」「只是看看」「规则修改」「用户让主控亲自做」等执行例外。若用户确实要当前会话亲自执行，必须先明确取消或变更该项目的主控绑定，再按新角色处理。

## 双通道路由（子代理树 + 会话图）

DSH 里主控有两条派发通道，**职责不同，按容器性质选，不要混用**：

| 通道 | 建出来的东西 | 何时用 | 续派方式 |
| --- | --- | --- | --- |
| `subagent(description, prompt, run_in_background)` | **子代理**：`origin=subagent` / `delegationDepth≥1`，不在侧边栏顶层，`session_list` 也看不到 | 默认。同业务域内可复用的常规执行容器 | `send_message(agent_id, …)`，**只能由创建它的那个主控会话续派**（depth-1 限制） |
| `session_spawn({task, title?})` | **顶层会话**：与侧边栏同级、持久、`session_list` 可见 | 需要①跨主控会话续派、②独立顶层身份（用户可在侧边栏直接打开/接手）、③不随本会话上下文一起失效 的容器 | `session_send({to: <id>, text})`，**任何会话都能续派**，不要求是本会话的子代理 |

按顺序判断，命中即停：

1. 该业务域已有合适的直接子代理 → `send_message`（首选，见「按业务域复用」）。
2. 需要**新的**执行容器，且只需本主控会话续派 → `subagent`（默认）。
3. 需要新容器，且**必须能被其它会话续派**、或必须有独立顶层身份 → `session_spawn`。
4. 用户明确要求"开一个独立的顶层会话来做" → `session_spawn`。

`subagent_fork` 仍然**不能**当可续派容器（fork 是一次性的）；它缺的正是 `session_spawn` 补的这一位：顶层、持久、任何会话都能继续投递的容器。

**回复链必须写进派发 prompt。** `session_spawn` **没有**自动回信协议：被创建的会话能从首条消息前缀看到发起方 sessionId，但不会主动回信。所以用它派活时，`task` 里必须显式写明：

```text
完成后调用 session_send({ to: "<主控 sessionId>", text: "<结果摘要>" }) 把结果回给主控。
```

否则结果没人收——而主控又被禁止主动轮询/跟踪（见「派发事务」第 7 步与「禁止事项」）。

**看不到别人的工作内容。** `session_list({verbose:true})` / `session_status` 只返回 id、标题、cwd、所属工作区、运行状态（`waking`/`running`/`idle`/`offline`/`archived`/`missing`）；`session_messages` 只读**投递给本会话**的消息，**不是**读别人的对话或工作过程。DSH 没有 `read_thread` 等价物，主控**仍然无法**窥探其它会话的内容——不要把它写成"能看到"的能力。

## 派发事务（DSH 版）

每次用户请求只执行一次：

1. **识别业务域**：从业务目标、数据所有权、状态机、外部平台和已有需求主线识别「项目 + 持久业务域」，不要先按 bug/feature 或技术层分类。
2. **选择容器**：用 `list_agents` 看本会话已有的直接子代理，选最匹配的持久业务域。优先复用，不扩容。
3. **派发**：
   - 已有子代理处于 `idle` 或 `ready` → `send_message(agent_id, prompt)`（会启动新的一轮）。
   - 已有子代理正在 `running` 且属同一业务域 → 用 `send_message` 排队/追加，它会在最近的一个步骤边界收到。
   - 确实没有合适容器且已获授权 → `subagent(description, prompt, run_in_background: true)`，拿 durable agent id。
   - 需要顶层独立、可被其它会话续派的容器且已获授权 → `session_spawn({task, title?})`，并把回复约定写进 `task`（见「双通道路由」）。
4. **投递判定**：`send_message` 返回成功即已投递，返回失败即**未投递**——DSH 不存在 Codex 那种「工具成功但消息退化成 `functionCallOutput`」的情况。**因此不需要读一次目标会话做送达核验。**
5. **唯一允许的一次核对**：子代理的**结算通知**由运行时自动送达。通知到达时核对其中是否带本次任务编号：
   - 带编号且内容与本次任务相关 → 事务完成。
   - 通知缺失、只复述旧口径、或与本次任务编号无关 → 判定该子代理不可健康承接，转第 6 步。
6. **不可承接时的处理**：
   - 不得向用户宣称派发成功，也不得沿同一条失效路径反复重试。
   - 将该子代理标记为当前不可健康承接（可验证理由：历史冲突、持续恢复旧上下文、上下文过长、对多个不同任务给出同一陈旧回复）。
   - 若用户当前已授权新建 → 用相同业务域命名新建一个干净子代理，把本次任务作为它的首条 prompt；**不得用 `subagent_fork`**（fork 是一次性的，无法被后续续派复用）。
   - 未获授权 → 保留原容器并向用户说明核验失败及需要新建授权。
7. **立即结束**。收尾话术必须明确「派发完成，业务结果由执行子代理交付」，不得把投递成功报告成业务完成。

**禁止**：`list_agents` 轮询、`job_output` 等待、`wait: true` 阻塞、heartbeat、因完成/失败状态自动介入、自动验收、自动继续派发。整个生命周期结束后，不再读取执行进度。

## 新建前的 Git Worktree Preflight

**只在**已满足「确实没有合适执行子代理」且「当前请求或项目配置已授权新建」两个前提后才运行：

```bash
ruby ~/.dsh/skills/dsh-main-control/scripts/worktree_preflight.rb "<project_root>"
```

只执行 `git -C <root>` 下的 `rev-parse`、`symbolic-ref`、`rev-list`、`show-ref`、`worktree list` 等只读命令并输出 JSON。它检查：是否真实位于 Git work tree、`HEAD^{commit}` 是否有效、仓库是否缺少初始提交、`HEAD` 是正常分支/unborn/detached、当前分支对应的 `refs/heads/<实际分支名>` 是否真实存在、`git worktree` 是否可用。

`subagent` 没有隔离参数，所以 preflight 的结论**决定 prompt 怎么写**，不是决定工具参数：

| Preflight 结果 | 写进 prompt 的指令 |
| --- | --- |
| Git work tree；`HEAD` 有效 commit；正常本地分支；该分支 ref 存在；worktree 可用（`isolated=true`） | **要求子代理先建隔离 worktree 再改动**（用项目规定的脚本，如 `scripts/prepare-dev-worktree.sh`） |
| 非 Git work tree | 就地执行，**并禁止任何 Git 写操作** |
| 无初始提交 / unborn 分支 / `HEAD` 无法解析 | 就地执行，禁止 Git 写操作 |
| 分支 ref 缺失或引用状态无法证明 | 就地执行，禁止 Git 写操作 |
| detached HEAD，即使 commit 有效 | 就地执行，禁止 Git 写操作 |
| preflight 异常、Git 不可用或结论不确定 | 就地执行，禁止 Git 写操作 |

分支可以叫 `master`、`develop`、`codex/xxx` 或任何合法名称，**不得假设默认分支叫 `main`**，也不得为方便而擅自传入或创建 `main`。

Preflight 及故障恢复过程中**严禁**执行 `git init`、`git branch`、`git switch`、`git checkout`、`git commit`、`git update-ref`、写操作 `git symbolic-ref`、`git worktree add/remove`，不得创建空提交、修改默认分支或提交用户改动。

> 注意：项目根目录本身常常不是 Git 仓库（例如根目录下只放了几个子仓库）。这种项目 preflight 会返回 `not_git_work_tree`，属于正确结果——隔离级别应按**具体子仓库**判断，把子仓库路径传给 preflight。

## 最小可交付闭环 / MVP

- 把「容器」和「MVP」分开：子代理代表长期稳定的业务域；MVP 代表该业务域内本次可独立验收的最小任务。同一业务域可以按顺序承接多个带唯一编号的 MVP。
- MVP 必须是 prompt 允许范围内**可独立运行、可独立验收**的最小业务闭环。中间步骤、半成品、未接通接口、只有代码没有验证的实现，都不算 MVP。
- 用户只要求诊断时，MVP 是证据充分、边界清晰、可复核的诊断结论（根因或已证实的原因范围、关键证据、影响面、风险、建议），**不得擅自改代码或发布**。
- 用户要求实现时，MVP 包含实现该业务结果所必需的代码、契约衔接、测试或运行验证，以及当前请求或项目既有授权覆盖的提交、发布或回写；把授权来源、目标环境、范围和终点明确写进 prompt。
- 核对当前请求、已有确认和项目发布规则后仍未获发布授权时，终点写「不发布」。不遗漏已有授权而重复询问，也不把通用「修复/改好」或 dev/test 授权外推成生产发布授权。
- 用户明确授权发布或外部回写时，把目标环境、入口、终态和读回证据写进同一个 prompt，让子代理自己跑完整链路，主控不介入。
- 不为追求「完整」扩大到用户未授权的业务、环境、仓库、数据或破坏性操作。

## 默认从简

- 以用户可见问题的直接链路为默认范围。先修已复现的入口，不因「理论上可能相关」自动盘点所有相邻接口。
- 相邻入口、缓存、向量、索引、性能、历史数据和架构治理，只有在**用户明确要求**、**已有证据表明它们同样失败**、或**不处理它们就无法成立**时才纳入；否则最多在最终结果里用一句话记录风险。
- 不把业务不变量展开成穷举式检查清单。不变量用于防止明显破坏，不用于制造新的实施范围。
- 验证强度与改动风险成比例。小改动默认完成：一个直接复现、一个聚焦测试或项目规定编译、一个目标接口 smoke。不要为「更充分」重复做静态检查、全量启动、执行计划、索引审计和多组正反样本。
- 项目已有编译、测试或发布脚本时使用它们，但不要在脚本已证明同一事实后再换另一种方式重复验证。
- 本地运行被无关外部依赖阻塞时，记录一次明确阻塞即可；不要连续补齐数据库、Redis、对象存储、AI 等与当前需求无关的凭据来强行启动。
- 发布任务只等待与本次改动相关的部署和健康检查，不为宣告完成而等待无关任务。
- 达到用户要求的验收标准后立即停止，不追加「顺手治理」、文档扩写、性能优化或未来兼容层。
- 简单任务的派发 prompt 控制在一屏左右；背景只保留执行者无法自行发现且会改变实现的事实。

## MVP 边界与依赖

- 按「可独立交付并独立验收的业务结果」划分 MVP，按持久业务域划分容器。**不得把一个新 MVP 自动解释成一个新子代理。**
- 若 B 依赖 A 的接口或产物、C 又依赖 A+B 联调，则 A→B→C 属于同一个 MVP，交给同一业务域子代理按序完成。
- 多仓库、多语言、多技术栈、多 worktree 或步骤多，都**不是**拆分 MVP 或容器的理由；只要产物必须顺序衔接，就由同一业务域容器保持契约、联调上下文和最终责任。
- 不提前创建下游集成或发版任务来占位。把 prompt 中已授权的下游步骤交给同一业务域子代理在前置条件满足后继续完成。
- 只有工作流彼此独立、可分别运行、可分别验收且没有共享联调状态时，才允许拆成多个 MVP。每个 MVP 仍按业务域路由；只有业务域确实不同、各自都没有合适容器、且当前请求明确授权新建或项目配置允许自动创建时，才使用多个新子代理。

## 按业务域复用

- 先用 `list_agents` 列出本会话的直接子代理，结合描述、既有任务编号、代码模块/服务、长期需求名、分支、commit 或外部平台名交叉判断，**不要只看 description 字符串**。
- 业务域由稳定的业务所有权决定，例如支付与分账、账号绑定、内容审核、即时通信、会员积分与优惠券、订单履约；不要按前端/后端/数据库、bug/feature、截图/接口或本次症状拆容器。
- 选择优先级：
  1. 同项目、同业务域、持有相关代码与历史决策的子代理。
  2. 同项目、同 bounded context，且能保持同一状态机或数据契约的子代理。
  3. 项目通用执行容器，仅用于没有稳定业务归属的一次性运维或杂项。
- 候选正在 `running` 不降低业务匹配优先级。相同业务域的新 MVP 继续用 `send_message` 排队，**禁止因占用创建 `bug-2`、`bug-3`、`feature-2` 或其它编号副本**；但已按「派发事务」第 5-6 步证实不可健康承接的，不属于健康候选。
- 一个请求跨前端、后端、数据库、联调和发布，只要共同交付一个业务结果，就由同一业务域子代理按依赖顺序完成。
- 若用户要求并行，但多个任务属于同一业务域且共享契约，仍优先在同一容器顺序完成；只有业务结果真正独立时才拆分。
- **禁止复用**：跨项目、业务所有权冲突、明显过期会误导、核验失败、上下文冲突已影响执行、或角色本身是主控的子代理。
- 每个 prompt 带唯一任务编号或工单 ID，使同一容器可安全承接多个顺序 MVP。

## 模型与权限

- **策略：所有子代理统一使用与主控相同的模型。** 这是本项目已确认的既定选择，不是权宜之计，也不需要重新评估。
- 机制（已核实到源码）：`subagent` 调用不传 `provider` / `model` / `reasoning_effort` 时，子代理直接继承父 Agent 的 provider、model 与 reasoningEffort；插件在 `agentOptions` 未配置时**连模型路由预检都跳过**，属于纯继承。
- 因此**不需要任何配置改动**：不要开启 `modelSelectionSettings`，不要配置 `agentOptions`。主控会话用什么模型、什么 reasoning 档，子代理就用同样的。
- Codex 版那条「必须显式传模型和思考档位参数」在 DSH 下**不适用也不需要**：`subagent` 默认不暴露模型参数，若要显式传参反而会打断继承，属于禁止行为。
- **不要在 prompt 文本里声明模型**——文本不是配置事实源，而且会让执行子代理误以为可以自行换模型。
- 派发汇报口径：直接说「子代理继承主控模型」。**不要凭空断言具体模型名**（主控并不读取 LLM 配置，说了就是编），也不要把"未传模型参数"说成"模型未指定"。
- 唯一例外：用户在当前请求中明确要求某个子代理用不同模型或 reasoning 档。此时以当前请求为准，但要真正落实它需要开启 `modelSelectionSettings`（属 harness 配置改动），必须用户明确同意后才改。
- 默认选择工具允许的最大自动权限和最低确认阻力，让只读、定位、编译、构建与验证命令不反复请求确认。
- 自动权限不等于扩大业务授权。生产、支付、财务、数据库、部署和凭据任务仍遵守项目规则与相关安全 skill。

## 风险边界写进 Prompt

- 在 prompt 顶部明确目标环境、允许修改和操作范围，以及禁止写错库、推错分支、未授权正式发布、删除文件、重置分支和破坏性 SQL。
- 对生产、支付、财务、数据库和部署任务，写清环境、账号、服务、分支、脚本入口与回滚/停止条件。
- 需要高风险动作但用户尚未授权时，列为禁止项或外部依赖，**不得让子代理自行推断授权**。
- 已有批准只覆盖原目标、环境和影响；专项明确要求的逐次确认仍须遵守。需新增批准时，子代理先完成不依赖该批准的工作和可审阅方案，仅暂停受影响动作。
- 复杂任务要求子代理先写计划再自行完成 MVP；计划不构成需要主控逐阶段批准的停点。

## 默认精简 Prompt 模板

```text
请在【项目路径】处理【任务名】。

任务编号：【唯一编号/工单 ID】
业务域：【持久业务域；复用哪个子代理及一句话理由】

目标：
- 【用户要求的直接业务结果】

范围：
- 做：【完成目标必需的入口、文件或系统】
- 不做：【相邻但本次无证据、无必要的内容】

验收：
- 【一个直接负向/问题用例】
- 【一个正常正向用例】
- 【项目规定的最小测试或编译】

环境与 Git：
- 【preflight 结论：先建隔离 worktree，或就地执行且禁止 Git 写操作】

权限与终点：
- 【只读/允许修改；是否提交、发布、回写】
- 【已有授权来源、目标环境与范围；仍需满足的明确审批】
- 【禁止的高风险动作】

会话策略：
- 简单任务直接执行；复杂任务只写简短计划。
- 达到上述验收即停止，不扩展相邻治理。
- 完成后简要汇报结果、验证和真实限制。
```

仅在任务真实需要时增加数据库、发布、回写、回滚或跨系统字段；**不要把可选字段全部展开**。

## 用户显式后续请求

- 用户明确查询状态时，定位目标子代理并按需做一次必要查询，简要返回当前事实；**不要附带后续定时检查**。
- 用户明确补充任务或纠偏时，把新增边界一次性 `send_message` 到同一合适容器，完成投递后立即结束。
- 用户明确要求验收时，把验收定义为该业务域内新的最小可交付闭环，默认续派原业务域容器；只有用户明确要求独立验收容器时才另行选择或创建。
- 不把子代理自行汇报、状态变化或历史终态视为主控可以主动采取新动作的授权。

## 禁止事项

- `role=main_control` 时不得亲自执行任何项目细节；没有执行槽、没有匹配容器或用户要求亲自执行时也不得接管。
- 除派发事务所需的一次投递判定、以及子代理结算通知到达时的一次编号核对外，派发成功后**不得**主动等待、跟踪、验收、纠偏、继续派发或读取任务状态。
- 不要把 `bug/feature`、技术层或单次症状当成长期容器边界。
- 不要因既有业务域容器忙碌而新建编号副本；相同业务域必须排队复用。
- 不要无授权静默新建容器。只有确实没有合适容器，且用户当前明确要求或项目 `auto_create_execution_threads=true` 时才创建；字段缺失或为 `false` 的项目仍须逐次询问。
- 不要把「项目根不是 Git 仓库」误判为 preflight 失败，也不要跳过只读 preflight，更不要为让 worktree 成功而执行任何写 Git 操作。
- 不要用 `subagent_fork` 充当可复用执行容器（fork 是一次性的，无法续派）；需要顶层、可跨会话续派的容器时用 `session_spawn`。
- 用 `session_spawn` 派活时不要漏掉 prompt 里的回复约定（让对方向主控 `session_send` 结果），也不要声称主控能读取被派发会话的工作内容——`session_messages` 只读投递给本会话的消息。
- 不要虚构 `clientThreadId`、setup 排队状态、`::created-thread{}` 或会话标题——DSH 没有这些概念。
- 不要声称已设置主控会话标题（DSH 无对应工具），也不要凭空断言子代理使用的模型名。
- 不要给子代理单独指定模型：不得传 `provider` / `model` / `reasoning_effort`，不得开启 `modelSelectionSettings`，不得配置 `agentOptions`——统一继承主控模型是既定策略。
- 不要按技术层、仓库或执行阶段拆分同一个强依赖业务闭环。
- 不要把最小 MVP 写成半成品，也不要擅自扩大到未授权发布或外部回写。
- 不要把最大自动权限理解成可以跳过项目发布、数据库或生产安全规则。
- 不要把跨项目子代理当作上下文复用。
- 不要只把机制写在项目文档里；本 skill 是全局默认机制，项目文档只能补充业务事实。
